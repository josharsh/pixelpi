# Controlled PixelPi / Playwright comparison

This suite compares **browser tools driven by a fixed program**, without an LLM. It does not measure autonomous agent task-solving, model cost, or production-site reliability.

Three systems run the same ten local UI workflows:

- PixelPi 0.6.1 over its actual stdio MCP server.
- Playwright MCP 0.0.83 over its actual stdio MCP server.
- Direct Playwright scripts, using the same Playwright dependency version as MCP.

Playwright is a pinned development dependency only. PixelPi uses its own CDP substrate in production. The baseline artifacts preserve the original implementation; later result directories identify the tested fix revision.

## Run

```sh
pnpm install --frozen-lockfile
pnpm build
node --import tsx --test bench/comparison/refs.test.ts
pnpm exec tsx bench/comparison/run.ts --repeats 5 --out bench/results/my-comparison --require-all-pass
python3 bench/comparison/summarize.py bench/results/my-comparison
```

Requires local Google Chrome. No API key, external website, browser login, or Docker installation is needed. Use a new output directory for each run; existing raw results are never overwritten. A local HTTP server serves the synthetic fixtures. All submissions go to that server.

## Protocol

The tasks and their exact expected outcomes are defined in `fixture.ts`. Six basic scenarios test extraction, search/detail navigation, a blank form, a dropdown, a checkbox, and locating the last of 240 buttons. Four stress scenarios test replacing prefilled values, clicking a temporarily disabled button, open Shadow DOM, and a same-origin iframe. These are intentionally selected diagnostic cases, not a representative random sample of websites.

Each system gets five repetitions of each task, a fresh browser/process, and a unique fixture run ID. The execution order rotates across systems by task and repetition. The browser engine is the same installed Chrome; Playwright's viewport is set to PixelPi's observed native viewport. Model calls, repair, and retries are absent. The controller uses the public fill, click, select, navigation, and evaluation APIs, without alternative strategies after a failure.

PixelPi and Playwright MCP resolve exact accessible role/name pairs from the text shown to a client. PixelPi pagination is followed when needed, and every page is charged. In the pinned Playwright release, automatic action snapshots are file links. The controller calls `browser_snapshot` to obtain their full inline content and includes that extra call in latency and token accounting. Responses without snapshots retain existing references. This is a **full-snapshot MCP workflow**. An agent reading selected lines from snapshot files, using a scoped snapshot, or using direct selectors may incur different costs.

Direct scripts use Playwright's role locators, `fill`, `click`, `selectOption`, and `frameLocator` for the iframe case. Scripts are hand-authored, not generated by a model. They have no tool-definition or model-context cost. That baseline answers whether PixelPi is faster than ordinary scripted automation; it does not stand in for an AI agent.

## What is measured

- **Correctness:** exact extracted value or exactly one server-received event matching the expected payload. The grader observes outside the tools and cannot accept a success message as proof. No-event, wrong-field, and duplicate-event cases fail.
- **Task time:** elapsed navigation-through-last-action time, including MCP transport and controller ref parsing. Browser startup and warmup are recorded separately. Tokenization and the grader's event-delivery wait are excluded.
- **Context:** `o200k_base` token counts for tool argument JSON and text responses, counted once. Definitions are reported separately with compact, pretty-printed, and normalized compact serialization. These are not billed tokens or total conversation tokens. Repeated history, model reasoning, prompt caching, and tool-selection behavior are unmeasured.
- **Silent failure:** the scripted plan finished without a tool/transport error but the independent grader rejected the outcome.

Task timings must only be compared over tasks completed by both systems. Failing quickly is not a speed advantage. Use per-task medians and ranges over repetitions; do not present the small fixture suite's pass fraction as a general reliability percentage.

Default waiting behavior is deliberately preserved. Playwright MCP waits for work to settle after many actions; PixelPi uses its own DOM-quiet wait. This affects latency. A real model's thinking time can dominate these differences and can also mask a disabled-button timing problem.

## Artifacts and limitations

`manifest.json` records task definitions, versions, environment, and source hashes. `trials.jsonl` contains every result and raw tool transcript. `tool-definitions.json` and `environment.json` preserve schema text, tokenizer counts, viewport, and browser information.

The acceptance flag exits nonzero if any trial fails. CI runs the browser regressions and a one-repetition comparison, and uploads the raw artifacts.

The summary script checks for missing, duplicate, and unexpected trials before writing aggregates. Add `--chart` in a Python environment with Matplotlib installed to generate PNG and SVG versions. The [technical article](../PLAYWRIGHT_COMPARISON.md) includes the measured results and interpretation.

The exact source protocol was debugged in excluded single-repetition pilot runs before the measured five-repetition run. Pilot controller problems are not product failures. The final run keeps all task failures; no tuning of PixelPi or Playwright production code occurs between trials.

This suite does not test arbitrary task understanding, screenshot-driven interactions, authenticated sites, CAPTCHA, downloads, cross-origin frames, mobile browsers, or repair after website changes. More tools in Playwright MCP provide capabilities that PixelPi may not expose. Smaller definitions alone do not mean equivalent capability.
